## Severity 1: design flaws that will not work### F1. `permissions: allow` "picks dsh's first allow option automatically" violates the stated contract semantics**verified.** The ACP contract says `session/request_permission` is "a permission prompt with one-shot allow/reject choices." Nothing in the contract guarantees the first option is an allow choice, that option ordering is stable, or that option ids are meaningful outside opaque choice identifiers. Picking "the first allow option" by ordinal or by guessing which id means "allow" is not specified by the contract. ACP permission responses must be sent using the option ids dsh sent, as the design itself states elsewhere for `answer` with `choice` being "one of the option ids dsh sent (allow once, reject, and whatever else dsh offers)." The `permissions: allow` path as specified cannot be implemented reliably from contract facts alone. The builder would need dsh-specific knowledge of option id values, which the contract calls "opaque."### F2. `session/cancel` with no in-flight prompt "cancels autonomous work" but the design uses `cancel` as a pending-question resolver**verified.** The contract says "without an ACP prompt in flight it cancels autonomous work." The design says `cancel` "resolves pending items of that session as rejected or cancelled so dsh's tools can finish." This is a plausible reading of "autonomous work" for a blocked `ask_lead` tool call, but it is not guaranteed. The contract also says "Later child messages may start autonomous work and do not delay the cancelled response." It is unverified whether `session/cancel` interrupts a blocked MCP tool call inside a descendant. If dsh's implementation treats a blocked tool call as part of the active prompt, cancellation may wait on the tool call to return, which it cannot until `answer` arrives, which the lead may never send. Deadlock. The design needs an explicit `answer` with a rejection before cancel, or a tested path proving cancel unblocks the tool call.### F3. `ask` as "`start` plus `follow` in one call" cannot work as a blocking tool in Claude Code**verified/inferred.** Claude Code invokes one tool per turn; the tool must return before Claude can invoke the next. `ask` blocking up to 3600 seconds while the plugin model inside dsh asks `ask_lead` questions means the lead Claude session cannot call `answer` because it is still waiting for `ask` to return. The MCP server is single process, and the pending queue only drains when some client calls `follow` or `answer`. A single `ask` tool invocation occupies the only client connection; no concurrent `answer` call can arrive. The design even says "A timeout does not cancel the run; the error names `session` and `runId` so the caller can `follow`," which admits the normal path is: `ask` times out, then the lead calls `follow`, sees pending, calls `answer`, then calls `follow` again. That is not `start` plus `follow` in one call; it is `start` plus `follow-with-timeout` plus `answer` plus `follow`. The `ask` tool as specified either blocks until timeout whenever any question or permission is raised, or it must internally auto-answer, which contradicts the stated anti-goal of never answering without the lead. The design must decide: `ask` is a convenience that only returns final when no pending items occur, and otherwise returns early with pending state, or `ask` is removed.### F4. The lead-bridge is declared as an MCP server in `session/new` without the ACP client verifying the absolute command survives session persistence and resume**verified.** The contract says `session/new` validates "stdio with absolute command" and a "connection failure rolls the session back." The design says `session/resume` "re-declares MCP servers" with a new socket path. This requires the MCP server process to know its own pid (`<server-pid>.sock`) and pass that into `session/resume`. That is fine for the design's own process. But if the MCP server exits while a session is persisted, then a different frontend (dsh web UI, another Claude session, `dsh-subagent-acp`) resumes the same session, the lead-bridge command path still points at the old socket and the old server pid. The contract says `session/resume` verifies "absolute workspace" before composition; it does not say the client revalidates MCP server command reachability on resume. If the path is stale, the resumed session's `ask_lead` tool fails with "lead unreachable" forever even though a new lead exists. The design does not cover cross-frontend resume of sessions with a dangling lead-bridge declaration.### F5. "Once a session id and prompt are known to have reached dsh, never resend" cannot be enforced by the MCP server alone**inferred.** The anti-goal depends on knowing whether `session/prompt` was accepted before a transport error. ACP over stdio is a JSON-RPC stream. If the MCP server crashes after dsh accepts the prompt but before the response is read, the plugin cannot know the prompt was accepted. The design's `detached` status admits "the run's fate is unknown." The agent prompt can say "never resend," but the bridge agent cannot distinguish "prompt accepted, reply lost" from "prompt never sent." The `detached` state plus a "never resend" rule means the lead must either abandon the session or manually inspect dsh's session list. The design should specify a recovery path: `sessions` lists persisted sessions with their last known state, and `start` with a `session` on a detached run should resume and prompt again only if the session's last prompt did not produce a turn, which the plugin cannot know from ACP. This needs an explicit builder decision with a tested procedure.## Severity 2: unaddressed risks### R1. One-prompt-in-flight rule vs. blocked `ask_lead` tool call**verified.** The contract says "one prompt at a time per session." A dsh model calling `ask_lead` blocks inside the active prompt until `answer` arrives. While that prompt is blocked, no other prompt can start on that session. The lead cannot send a follow-up `start` to the same session, and cannot `cancel` without risking the pending question path (see F2). If the lead never receives the pending question because the bridge agent's `follow` call returned no pending items due to a race, the session deadlocks until a timeout. The design needs an explicit invariant: before `start` is rejected as "prompt in flight," the MCP server must check whether the only in-flight activity is a blocked `ask_lead` and surface that as `waiting`, not `running`.### R2. `follow` cursor correctness across reconnect and child restart**verified/inferred.** The design keeps an "event buffer" in the MCP server. If the dsh child dies mid-run and restarts, `session/resume` does not replay old updates per the contract: "its log is restored without replaying old updates." Any events the buffer lost because the MCP server also restarted are gone. The event buffer must be durable if cursors must remain valid across MCP server restarts, because the `after` cursor is an opaque value the bridge agent may present after a restart. The design does not say whether the cursor is an integer index into a memory buffer or a durable offset. If the buffer is in memory and the server restarts, a stale cursor can produce missing events or an error. This must be specified and tested.### R3. `session/resume` requires the canonical workspace to be verified; `cwd` changes invalidate resume**verified.** The contract says `session/resume` verifies "the canonical workspace before composition." The design lets `start` with `session` resume "if it is not live." If the lead passes a different `cwd` than the session's original workspace, dsh will reject the resume. The MCP server must map the error to a clear message. The design does not specify this error path.### R4. Multiple MCP sessions in the same Claude Code session: two sessions, one cwd, one pending session**verified/inferred.** `models` "creates a session in `cwd` and keeps it as the pending session for that cwd." `start` without `session` reuses the pending session. But `start` can also create a fresh session in the same cwd if the caller explicitly wants one. The pending-session-per-cwd keying breaks when two bridge agents in the same Claude session work in the same cwd with different dsh sessions. The design does not state whether `start` without `session` should reuse the pending session always or only if no explicit session was ever provided. Race conditions between two agents calling `models` and `start` concurrently are unspecified.### R5. `session/close` drains descendants; the design calls `session/close` on every live session at MCP server shutdown**verified.** The contract says closing "also drains its descendants." If a session has a blocked `ask_lead` and the design resolves pending questions with "lead gone" before closing, that is consistent. But if the resolution order is wrong (close before answer), the close may hang waiting for the blocked tool call. The design says "resolves pending questions with 'lead gone', and then ends the child" but the implementation order relative to `session/close` is not pinned. Shutdown must answer or reject all pending items before any `session/close`.### R6. The child's stdin EOF is the idle shutdown signal, but EOF is also what happens when the MCP server receives SIGTERM**verified/inferred.** The design uses stdin EOF for both idle shutdown and forced termination. If dsh treats EOF as a graceful shutdown that waits for active prompts, the "few seconds" best-effort shutdown may not hold. If dsh treats EOF as immediate termination, idle shutdown loses persisted state. The design needs to distinguish: send `session/close` for each live session, then close stdin, then wait a bounded time, then SIGKILL.### R7. Socket security: frames carry session id, server verifies "it belongs to a live session" but not the requesting process identity**verified/inferred.** The socket is mode 0600 under a per-uid directory, so other users cannot connect. But any process running as the same uid can connect. A malicious or buggy local process can send `{ session, tool: "ask_lead", args: { question: "..." } }` to a live session and inject a question the lead sees. The design calls the session id verification sufficient; it is not authentication. Given dsh is running with the user's full credentials, this is a local privilege boundary issue. The severity is mitigated by same-uid equivalence in practice, but it should be stated.### R8. `after` cursor 0 conflicts with a legitimate event id**inferred.** The design says `after` has "0 first" meaning first call uses 0. If events are numbered from 1, that works. If event ids are strings or Unix timestamps, 0 is a special case. The design defers cursor encoding to the builder; a builder implementing this may accidentally make `after: 0` return all events or none depending on off-by-one handling. Needs a contract-level test.## Severity 3: missing pieces a builder needs### M1. Exact `session/request_permission` answer format**verified.** The contract says choices are "one-shot allow/reject," but the actual ACP message format for answering a permission request is not in the quoted contract. The builder must consult `@agentclientprotocol/sdk` or the dsh reference client for the exact field names and whether answering requires the request id, the option id, or both.### M2. How `answer` for a `question` becomes "the tool result inside dsh"**verified.** The lead-bridge receives `{ result }` over the socket and returns it from its MCP tool. But the dsh model's tool call protocol requires a specific MCP response shape. The design does not specify how long the lead-bridge blocks inside the MCP tool call while waiting for the socket reply, whether the lead-bridge tool call has a timeout, or what happens if the MCP server answers after the dsh turn is cancelled.### M3. `models` advertised response shape**verified.** The contract says `session/new` returns "complete configuration-option state," and the design says models are advertised there. The builder needs the exact JSON path for provider/model options and the default route, plus how `session/set_config_option` reports changed options.### M4. `session/list` cwd filter semantics for `sessions`**verified.** The contract says "optional absolute cwd filter uses physical-directory identity where possible." The builder needs to know what `sessions` should pass when the Claude project has symlinks, and what `sessions` without `cwd` means (all sessions or only the current project's).### M5. The lead-bridge MCP tool schemas**inferred.** dsh will call `ask_lead` and `notify_lead` via MCP. The tool input and output schemas must be declared precisely, including whether `choices` is a string array and whether the tool result is plain text. dsh's MCP client may reject tools without a complete schema.### M6. `cancel` for a pending question before `answer`**inferred.** The design says cancel "resolves pending items as rejected or cancelled so dsh's tools can finish." The exact socket reply to the lead-bridge for a cancelled tool call must be specified: MCP error with a specific code, or success with a "cancelled" text result.### M7. Resume with a fresh socket requires passing the new socket path into `session/resume`**verified.** The design states this works, but the builder must implement: at resume, the MCP server must update its per-session MCP server declaration to point at the new socket before calling `session/resume`, and dsh must accept the changed MCP server command. The contract says session/resume validates absolute MCP server entries, but does not say whether changing the command between resume calls is treated as a different MCP server or replaced.### M8. Idle shutdown vs. pending sessions**verified.** The design says idle shutdown after 30 minutes "with no live session." If a session is live but has no in-flight prompt and its `ask_lead` tool is not blocked, does it keep the child alive indefinitely? The design says yes, because "no live session" is the trigger. A session that the user forgot to close will keep the dsh child alive forever. The design needs a separate timeout for live-but-idle sessions.## Severity 4: simplifications that keep the stated goalsThese are acceptable and should not be expanded unless the user asks.### S1. No `session/load`, no images, no resource links**verified.** The contract explicitly rejects these; the design's non-goals match.### S2. `history` from the plugin's own record, not dsh's store**verified.** The contract says `session/resume` "does not replay old updates"; no history call exists. The design's own record is the only option without reverse-engineering dsh's zstd transcripts.### S3. No custom agent types beyond `dsh`**inferred.** One agent type with a `model` parameter covers the stated goal of any task.### S4. `permissions: ask` as default**verified.** The anti-goal says never silently answer. Default ask matches.### S5. Web patch overlay instead of duplicating config**inferred.** The design explicitly avoids user-specific values in the plugin. Borrowing the web profile's patch is the least-bad option given dsh's per-profile config model.### S6. One dsh child per MCP server, not a shared daemon**verified.** The contract supports several sessions per connection; one child per Claude session avoids cross-session coupling and the design's `session/resume` with fresh sockets handles restarts.
