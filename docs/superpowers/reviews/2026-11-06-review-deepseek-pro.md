## 1. Design flaws that will not work**High: the blocking `ask` tool prevents answering questions and permissions. `[inferred]`**`ask` is defined as `start` plus `follow` in one blocking MCP tool call, returning only the final reply. The ACP contract has one prompt in flight per session, and dsh raises `session/request_permission` or an `ask_lead` tool call as pending items. While the Claude-side `ask` call blocks, the same bridge agent or lead has no returned `requestId` to pass to `answer`, so no answer can be sent. The run stalls until `timeoutSeconds` expires, default 600. This makes `ask` unsafe for any task that may ask a question or request permission, which directly conflicts with the bi-directional goal. Either `ask` must be non-blocking under `waiting`, or the bridge agent and direct command must be explicitly forbidden from using it except for known permission-free prompts.**High: `start` cannot return `runId` "as soon as dsh accepted the prompt" from the documented ACP call. `[verified]`**The contract says `session/prompt` settlement follows root and descendant completion plus ordered update delivery. That means the JSON-RPC call is in flight until completion. No early acceptance or admission receipt is documented. The design also says the anti-ambiguity rule depends on knowing the prompt reached dsh. With the documented contract, the client can know only that the request was written to the child, not that dsh accepted or admitted the prompt. If the child dies after the prompt was sent but before settlement, acceptance is unknown. A documented early `session/update` with a run id could fix this, but it is not in the provided excerpt.**Medium: `session/resume` MCP server redeclaration is load-bearing but not established in the provided contract. `[verified/inferred]`**The design says questions work after MCP server restart because `session/resume` redeclares the lead-bridge with a new socket. The provided contract excerpt says `session/resume` restores log and workspace and returns configuration state; it does not state resume accepts MCP servers. The design lists this as verified, but it is not supported by the quoted contract. Without it, resumed sessions keep the old lead-bridge socket and questions fail. This must be proven with a targeted integration test before the design is approved.## 2. Unaddressed risks**High: cancel can deadlock while dsh is blocked inside `ask_lead` or a permission request. `[inferred]`**`ask_lead` blocks inside the dsh session until `answer` or cancel. The design says `cancel` calls `session/cancel` and then resolves pending items. If dsh is synchronously blocked executing the MCP tool, it may not process the ACP `session/cancel` until the tool returns. But the tool will not return until the lead-bridge receives an answer or cancellation over the socket. The ordering must be defined: the MCP server may need to resolve the pending question or permission over the lead-bridge socket first, then call `session/cancel`. This is not specified.**Medium: multiple Claude sessions can resume the same dsh session concurrently. `[inferred]`**The design says several Claude sessions run several dsh children, and dsh persistence handles the shared store. It gives no per-session lease or ownership. Two MCP servers, or two Claude sessions, can both see the same persisted id via `sessions` and call `session/resume`. The contract only says resume targets a persisted inactive session. If two servers race on resume, one may win and the other fail, or worse, both may believe they own the session. A single-owner or explicit "already active" state is needed.**Medium: socket permissions and authentication are underspecified. `[inferred]`**The socket file is mode 0600, but the parent directory mode is not specified. It must be 0700. The session id in the frame is not an authentication mechanism. Any same-user process can connect and answer questions or inject tool results. Same-user trust may be acceptable, but the design should say so and should use `SO_PEERCRED` or another peer check if stronger isolation is intended.**Medium: unbounded event buffering and cursor lifetime. `[inferred]`**`follow` wants events since cursor `after`. The MCP server must buffer all `session/update` events between polls. There is no retention cap. A long-running dsh session with no `follow` calls can consume unbounded memory. Cursors from a previous MCP server process are invalid after restart, and the design does not define how `follow` detects that. The builder needs a bounded event buffer and explicit cursor invalidation.**Medium: model and reasoning changes must be ordered before `session/prompt`. `[verified]`**The contract says a prompt snapshots the selection and a concurrent option change applies to the next turn. When `start` receives `model` or `reasoningEffort` on a resumed session, the design does not state that it must call `session/set_config_option`, wait for the resulting state, and only then send `session/prompt`. If this ordering is not explicit, model choice can apply to the wrong turn.**Low: `permissions: allow` picking dsh's first allow option is ambiguous. `[inferred]`**The contract says permission prompts offer one-shot allow/reject choices. "First allow option" may not be stable or may include allow_once versus allow_always. The design must define exactly which choice id is selected and reject the run if that id is absent.**Low: `models` creates a session and therefore connects all configured user MCP servers. `[inferred]`**`models` creates a pending session to read model options. That session publication validates and connects the user's configured MCP servers. A broken or interactive server can make `models` slow or fail. This may be acceptable, but it should be called out as a side effect.## 3. Missing pieces- Exact ordering for `cancel` when a question is blocked, including whether lead-bridge resolution precedes `session/cancel`.- Direct command for answering or following a pending question. The listed slash commands include `/dsh:ask` but no `/dsh:follow` or `/dsh:answer`. A direct user whose task hits a permission request or question has no simple command path.- How `runId` is generated and when the client may treat a prompt as durably submitted.- Whether `session/resume` accepts new MCP server declarations, with a real dsh test.- Exact event schema, cursor encoding, and buffer eviction policy.- Sequence for `set_config_option` before prompt, including error handling if the requested model is not in the returned state.- Peer credential or same-user trust statement for the Unix socket.## 4. Simplifications that keep the stated goals- `history` as the plugin's own labelled record is a reasonable simplification. The contract has no history call and `session/resume` does not replay updates.- Reusing the pending session for `models` avoids throwaway sessions, at the cost noted above.- One bridge agent type is adequate. Model pinning is already a parameter.- Excluding images, terminals, plans, modes, and forks is consistent with the contract's known limitations.- The web patch overlay is a pragmatic way to reuse the user's dsh MCP and model configuration, assuming setup filters the three expected warnings.
